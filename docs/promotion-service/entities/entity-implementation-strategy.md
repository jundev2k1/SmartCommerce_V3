# Promotion Service — Entity Implementation Strategy

**Scope:** The binding, fixed order every aggregate follows starting Phase 2 (Domain Model). This is a process rule, not a per-entity spec — no entity exists yet, so nothing below names an actual Promotion type. Per-aggregate docs land under [../aggregates/](../aggregates/) as each one is implemented in this order.

This strategy is grounded in [../../conventions/domain-coding-conventions.md](../../conventions/domain-coding-conventions.md) (the platform-wide binding Domain-layer style rules) and verified against the actual shape of `Auth.Domain`/`User.Domain`/`Order.Domain`/`Product.Domain` — every step below names a pattern that already exists somewhere in this solution. Two terms from the original Phase 2.1 brief (`UpdateData`, `TranslationData`) do not correspond to anything in the codebase — see "Reconciliation" below for why they were folded into other steps instead of created as new wrapper types.

## Fixed order, per aggregate

1. **Entity** — the aggregate/entity class: identity (`Id`), base type (`AggregateRoot<Guid>` for a root, `BaseEntity`/`BaseEntity<Guid>` for a child — no surrogate `Id` on a 1:1 detail table or a pure mapping entity, Rules 4-5), `IAuditable`/`ITenantEntity` where applicable, private parameterless constructor.
2. **EntityData** — only when the aggregate's `Create` factory must build several children in one call (Rule 1 — e.g. an aggregate root that requires ≥1 child to exist meaningfully). Shape: a sealed record `Create{Entity}Data` (plus one nested record per child, e.g. `Create{Child}Data`) in `Entities/{Group}/Data/{Verb}{Entity}Data.cs` — see `Order.Domain/Entities/Orders/Data/CreateOrderData.cs`, `Product.Domain/Entities/Products/Data/CreateProductData.cs`. **Not every aggregate needs this** — a simple aggregate with no required child collection just takes flat `Create(...)` parameters directly (step 3).
3. **Properties** — scalar properties exactly as the architect's design specifies. No property invented to "seem complete."
4. **Navigation Properties** — plain `ICollection<T>`/reference navigation, `{ get; private set; }`, never a backing-field-plus-`IReadOnlyCollection` wrapper (Rule 3).
5. **Translation** — only for aggregates the design marks as localizable. A sibling `{Entity}Translation` entity in the *same* `Entities/{Group}/` folder (not a separate `Translations/` folder), reusing the parent's `Id` in a composite `(Id, LanguageCode)` key (Rule 5). The parent exposes `Translate(LanguageCode languageCode, ...flat params)` in a `#region Translations` block that upserts by language code (`FirstOrDefault(t => t.LanguageCode == code)` → `UpdateDetails(...)` or `{Entity}Translation.Create(...)`). **No separate `TranslationData` wrapper** — `Translate` takes flat parameters like every other Domain method (Rule 2); see `ProductBrand.Translate`/`ProductBrandTranslation` for the reference shape.
6. **Enums** — any enum the entity's properties require, added under [../enums/](../enums/) as it's introduced.
7. **Value Objects** — any Value Object the entity's properties require, added under [../value-objects/](../value-objects/) as it's introduced. Reuse `BuildingBlock.Domain.ValueObjects` where the shared type fits; only add a PromotionService-local Value Object when the shared one doesn't (same precedent Payment Service's local `Money`/`Currency` set — see [../../services/payment-service.md](../../services/payment-service.md#value-objects)). Every VO with validation exposes `IsValid`/`TryCreate`/`Create` over one shared `GetValidationError` (Rule 6).
8. **Owned Types** — EF-owned-type mappings for Value Objects with no identity of their own. Design only in Phase 2 (the actual `OwnsOne` mapping is written in Phase 3) — Phase 2 just confirms which properties are owned-type candidates.
9. **Indexes & Unique Constraints** — identify which properties/property-combinations need a query-supporting index or a uniqueness guarantee. Design only in Phase 2; written in Phase 3, catalogued under [../indexes/](../indexes/).
10. **Relationships** — confirm FK direction and cardinality for every Navigation Property from step 4: one-to-many, shared-PK one-to-one (Rule 5), or many-to-many via an explicit mapping entity — **never** a raw EF many-to-many or a primitive id collection (Rule 4).
11. **Structural methods** — every state change goes through a named, invariant-protecting method (`Add{Child}`, `Remove{Child}`, `Update{Aspect}`, `Activate`/`Deactivate`, ...), flat parameters always, grouped under `#region`s (Rule 0/2/3). **No `UpdateData` wrapper** — an update method's parameter list is flat, exactly like `ProductBrand.UpdateDetails(name, description, website, country, note)`, however long it gets. Child construction is `internal` where only the parent aggregate may call it (Rule 3's `Variant.Create` precedent).
12. **Aggregate Boundaries & Future TODO** — confirm which entity is the Aggregate Root and which are children only reachable through it (document under [../aggregates/](../aggregates/)); anything the architect's design references but explicitly defers gets a `// TODO:` comment in code and a one-line note in the aggregate's doc — never a guessed implementation.

## Reconciliation with the original Phase 2.1 brief

The brief's 12-step list named `UpdateData` and `TranslationData` as their own steps. Neither exists anywhere in `Auth.Domain`/`User.Domain`/`Order.Domain`/`Product.Domain`, and creating them would directly violate [domain-coding-conventions.md Rule 2](../../conventions/domain-coding-conventions.md#2-no-specrequestcommanddto-like-objects-inside-domain---flat-parameters-instead) ("No Spec/Request/Command/DTO-like objects inside Domain — flat parameters instead"): every update/translate method in the real codebase takes flat parameters, never a wrapper record. They're folded into steps 11 and 5 above instead of being created as new types. Two folder names from the brief's "Create Domain Structure" section were similarly not created for the same reason:
- **`Specifications/`** — not created. This codebase's Domain layer has no DDD Specification-pattern folder; Rule 1/2 explicitly reject Spec-wrapper objects. (Note: `Product.Domain/Entities/Specifications/` exists, but it's an unrelated *business* entity group — `SpecificationDefinition`/`SpecificationGroup`, a product-attribute catalog — not the pattern the brief meant.)
- **`Abstractions/`, `Aggregates/`** — not created. `Abstractions` is an Application-layer folder (see `*.Application/Abstractions/Persistence|Search|Services/`), never a Domain one. There is no separate `Aggregates/` folder in any service — an aggregate root is simply the entity at the top of its `Entities/{Group}/` folder; the boundary is documented (step 12), not folder-separated.
- **`Builders/`** — not created. No `*.Domain` project in this solution uses a Builder folder/pattern.

Folders that **were** confirmed real and added at `Promotion.Domain/` root in Phase 2.1 (all empty, populated only when an aggregate actually needs one): `Events/` (User.Domain precedent — domain events), `Metadata/` (Auth/User/Order/Product precedent — flexible per-entity metadata Value Object), `Constants/` (Auth.Domain precedent — domain-level default-value constants, e.g. `SessionDefaults`/`MfaDefaults`). `Entities/`, `Enums/`, `ValueObjects/` already existed from Phase 1.

## Rules

- No step is skipped. No step is reordered. No step for aggregate B starts before aggregate A's steps 1-12 are done, unless the design explicitly says two aggregates are implemented together (e.g. an aggregate root and a child entity with no independent lifecycle).
- No entity is created beyond what the architect's design specifies — this phase implements a design, it does not extend one.
- Steps that don't apply to a given aggregate (no bulk-create children → skip EntityData; not localizable → skip Translation) are skipped, not stubbed.
