# Changelog

## 2026-07-22 — `src/services/` DTOs moved inline, one file per endpoint (ADR 0012 amended)

Every backend service (`audit`, `user`, `order`, `inventory`, `product`, `notification` — `auth` already did this) had its `requests/`/`responses/` DTO subfolders removed. Each endpoint file now declares its own request/response interfaces directly, matching the pattern `auth/login.ts`/`register.ts` had used all along without anyone noticing the other six services were inconsistent with it.

- **Where a DTO is genuinely shared by more than one endpoint** — `CartResponse` (every `order` cart mutation), `CreateOrderResponse` (`POST /orders` and `POST /orders/admin`), `ProductVariationResponse` (`GetProduct` and `AddVariation`), `VariationInput` (`AddVariation` and `CreateProduct`), and every notification `*TargetInput`/`*TargetResponse` pair — it's declared once in whichever endpoint file most naturally owns it, and sibling files import it type-only from that file. Two response files that bundled 3 unrelated DTOs behind one filename (each backing a different endpoint — e.g. notification's `campaign.response.ts` holding `CreateNotificationCampaignResponse`/`NotificationCampaignSummaryResponse`/`GetNotificationCampaignResponse`) were split across their three respective owning endpoint files, since each interface really only had one consumer.
- **Opaque enum-like domain vocabulary is unaffected** — every service's `types/` folder (`order-status.ts`, `user-status.ts`, `warehouse-status.ts`, `product-category-status.ts`, notification's `enums.ts`, etc.) is untouched; only request/response DTOs moved. Two product `types/` files that turned out to be single-consumer object DTOs rather than shared enums (`product-category-item.ts`, `product-tag-item.ts`) were inlined into their one consumer (`list-product-categories.ts`, `list-product-tags.ts`) and deleted.
- Every service's `index.ts` barrel updated to drop the `requests/`/`responses/` re-exports (the types are already re-exported via each endpoint file's own `export *`).
- [decisions/0012-backend-service-client-layer.md](../decisions/0012-backend-service-client-layer.md) amended with an "Update" section recording this; `architecture/folder-structure.md`, and the `backend/audit/inventory/product/README.md` + `modules/authentication.md` file-path references that pointed at the old `requests/`/`responses/` paths, all corrected.
- Pure reorganization — no DTO shape, endpoint behavior, or consumer (`features/*.queries.ts`, `shared/commerce/*`) changed, since every external consumer already imported through each service's barrel (`@/services/<service>`), never a deep `requests/`/`responses/` path.
- `yarn typecheck`/`yarn lint`/`yarn build` all clean across the whole repo.

## 2026-07-22 — Real server-side Cart; `CreateOrder` split into client/admin endpoints

Backend session added a genuine Redis-backed Cart to the Order service and split `CreateOrder` in two. Frontend caught up:

- **Cart is server state now, not Zustand.** `shared/stores/cart.store.ts` is deleted; `features/cart/api/cart.queries.ts` (`useCartQuery` + add/update/remove/clear mutations, all invalidating the same `cartKeys.all` query) replaces it, per `docs/state/query-strategy.md`'s existing rule for server-backed entities. `CartPage`, `CheckoutPage`, `ShopSearchPage`, and `ShopProductDetailPage` all updated to call the new hooks instead of the store. **Real behavior change**: cart now persists across devices/browsers for a logged-in user, not just this browser's `persist`ed state — and "Add to cart" can now fail over the network (404/400), which it never could as a pure client store, so both Shop pages gained error toasts they didn't need before.
- **`CreateOrderRequest` dropped `customerId` entirely** — the caller's own auth session is always the identity now. Added `customerName`/`customerPhone` to the request; `CheckoutPage` sources these from `useCurrentUserQuery()` (via `toSessionUser().displayName` and `phoneNumber`). This also fixed a pre-existing bug found while touching this file: checkout wasn't sending `customerName`/`customerPhone` at all before this change, even though the backend already required them for an unrelated, earlier reason — see `docs/backend/order/README.md`'s prior "Also worth checking" note (now resolved).
- **`CreateOrderItemRequestDto` gained `variationId`** (and optional `discount`) — resolves the "no variation-level field on the wire" gap `docs/backlog.md`/`docs/modules/client-mock.md` previously documented. Checkout now builds order items directly from `useCartQuery()`'s data at submit time instead of keeping its own copy.
- **New `409 Conflict`** on `POST /orders` when `items` doesn't match the caller's current server-side cart exactly. `useCreateOrderMutation` invalidates the cart query on this path (not just on success); `CheckoutPage` shows a specific "your cart changed" toast instead of the generic error toast, and — since it always builds items from the live cart query — naturally avoids resubmitting the same stale snapshot once the cart refetches.
- **New admin endpoint `POST /orders/admin`** (`adminCreateOrder()`, `Admin`/`Root`-only, `customerId` required, no cart-diff check) — service function added, but no admin UI was built for it this pass; logged as available-but-not-built in `docs/backlog.md` §5, the same treatment already given to the Notification admin placeholders.
- **Minor, no-op-for-frontend change**: stock-availability is now checked before the catalog lookup server-side, so an insufficient-stock error message references the raw `variationId` instead of a resolved product name. Confirmed `docs/services/error-handling.md`'s toast rendering treats `message` as opaque text — no code change needed.
- Docs updated: `backend/order/README.md` (Cart endpoints, split `CreateOrder` contract, 409), `modules/client-mock.md` (removed the two now-resolved gap entries, updated flow description), `state/zustand-strategy.md` (removed the `cart.store.ts` bullet), `backlog.md` (removed the resolved variation-level-field row, added the admin-create-order not-built entry). `docs/tasks/backend-cart-and-order-split.md` (the task file this work was scoped from) deleted per its own "when this task is done" instruction.
- `yarn typecheck`/`yarn lint` clean.

## 2026-07-21 — Order fulfillment (Approve/Cancel), real OrderStatus labels, role-based nav + route guarding

Three changes landed together against the Order and Auth/Nav surfaces:

- **`OrderStatus` is no longer opaque.** Confirmed from backend source (`Order.Domain/Enums/OrderStatus.cs`: `Pending=1, Confirmed=2, Cancelled=3, Completed=4`) rather than Swagger prose. `services/order/types/order-status.ts` now exports a real const enum; `OrderStatusBadge` renders Pending/Confirmed/Cancelled/Completed labels with distinct badge variants instead of a raw number; `OrdersListPage`'s status filter dropdown now shows the same labels. Resolves the `OrderStatus (1–4) has no published name mapping` row in `docs/backlog.md` §2.
- **New backend endpoint: `CompleteOrder`.** The requested "Admin Approve List → Approve/Cancel" flow turned out to need a genuinely new backend capability, not a frontend-only build: `Order.Domain/Entities/Order.cs` already had a `Complete()` domain method, but no Application command or API endpoint exposed it. Added `POST /orders/{orderId}/complete` (`Order.API/Endpoints/CompleteOrder.cs`, `RequireAdmin`), `CompleteOrderCommand`/`CompleteOrderHandler`, and `OrderCompletedIntegrationEvent` (enqueued to the outbox, no consumer yet) to the SimpleShop backend — mirroring `CancelOrder`'s shape. See `docs/services/order-service.md` (backend repo) and `backend/order/README.md` (this repo).
- **New pages: Admin "Approve Orders" and customer "Order History".** `OrderApproveListPage` (`/orders/approve`, Admin-only) filters the same browser-scoped local-orders data to `status === Confirmed`; "Approve" calls the new `completeOrder` service function, "Cancel" reuses the existing `useCancelOrderMutation()`. `OrderHistoryListPage` (`/orders/history`, unrestricted) is the customer-facing equivalent of the admin Orders table, rendered as an `OrderSummaryCard` grid. Neither needed a new list endpoint — same `useLocalOrdersQuery()` constraint as every other order view. See `docs/modules/order-management.md`.
- **Role-based nav + route guarding.** `shared/config/nav.ts`'s `NavGroup`/`NavItem` gained an optional `roles?: string[]`; IAM/Catalog/Inventory/System are now `Admin`-only groups, the admin Orders table + new Approve Orders page are `Admin`-only items within the otherwise-unrestricted Sales group, and the four reserved Notification-admin placeholders are `Admin`-only. `Sidebar.tsx` filters `navGroups` against the session's roles before rendering; `AuthGuard.tsx` now also calls a new `getRequiredRolesForPath` helper on every route change and redirects to `/403` on mismatch — so hiding a nav entry and blocking direct navigation to it stay in sync, closing the gap where a `User`-role account could previously reach any admin URL directly. Added `AppRole` (`Root`/`Admin`/`User`, mirroring the backend's `BuildingBlock.SharedKernel.Constants.AppRole`) to `services/user/types/app-role.ts` — including `Root`, a backend superuser role the original ask didn't mention but which satisfies every policy check server-side, mirrored client-side so a Root-seeded account isn't wrongly locked out. See the new "Role-based navigation" section in `docs/modules/overview.md`.
- This is UI-layer defense only — it doesn't replace the backend's own per-endpoint authorization (`RequireAdmin`/`RequireAuthenticated`), which remains the actual enforcement.
- `yarn typecheck`/`yarn lint`/`yarn build` clean (frontend); `dotnet build` clean (backend, Order.API).

## 2026-07-20 — Phase 7: Notification Center & Realtime Experience

- `features/notifications` + a new presentational layer `shared/notifications/` (ADR 0017) implement the cross-cutting notification bell/dropdown/detail dialog — the single place responsible for notification UI in this app, per the brief.
- **`shared/hooks/useCursorList.ts`** (new, generic): the shared infinite-scroll wrapper `docs/decisions/0010-pagination-and-cursor-strategy.md` and `docs/state/query-strategy.md` had anticipated since Phase 0/1, built for real for the first time. **Real gap found while building it**: `ListMyUserNotifications` has no opaque cursor token at all — only `page`/`pageSize`, same as any page-based admin list. The hook drives `useInfiniteQuery` with a page number as `pageParam` instead of a true cursor, still delivering real infinite-scroll UX; both architecture docs updated to record this rather than silently diverge from what they described.
- **No reliable unread signal exists either**: the list DTO (`UserNotificationSummaryResponse`) has no `readAt` field (only the single-detail response does), and `NotificationStatus` is one of the 12 opaque, unpublished enums already flagged in `backend/coverage-report.md`. Rather than guess which value means "unread," `shared/stores/notifications.store.ts` now persists `readIds` (ids explicitly marked read through this UI via the real `MarkUserNotificationAsRead` endpoint); unread count/badge is "loaded and not yet marked read," not an authoritative historical count.
- **"Mark all as read"** is composed client-side from parallel calls to the real per-item mark-as-read endpoint (no bulk endpoint exists) — scoped to whatever's currently loaded, disclosed in the doc rather than silently partial.
- **Bell stays lightweight**: it fetches only page 1 (15 items) on mount to compute the badge — the dropdown reuses that exact same cached query (same key) rather than re-fetching, and only loads more as the user scrolls (a real `IntersectionObserver` sentinel, not a timer or full preload).
- **Realtime reuses Phase 6's infrastructure unchanged** — `shared/lib/realtime/useHubEvent.ts` and the auth-tied connect/disconnect lifecycle needed zero modification. `useNotificationRealtimeUpdates` subscribes to a placeholder `'NotificationCreated'` event (still no published event catalog from any of the 7 services) and prepends directly into the cached first page via `setQueryData`, incrementing the unread counter — no full-list invalidation.
- **Shell wiring**: `shared/layout`'s placeholder `NotificationBell.tsx` (Phase 1) removed; `Topbar`/`AdminShell` gained a `notificationSlot?: ReactNode` prop (same shape as Phase 2's `onLogout`, per ADR 0013, which explicitly anticipated this exact need) so `app/(admin)/layout.tsx` can inject the real, feature-owned bell without `shared/layout` importing `features/notifications`.
- Campaign/Rule/Group/Channel nav placeholders (already added Phase 1) were left untouched — confirmed still disabled/"coming soon," no business logic added, per the brief.
- `yarn typecheck`/`yarn lint`/`yarn build` all clean. One real lint **error** (not just a warning) surfaced and fixed during this phase: calling `Date.now()` directly during render in `NotificationTimestamp` violated React Compiler's purity rule — fixed by moving it into `useState`+`useEffect` (which also made the relative-time label refresh live while a dropdown stays open, a correctness improvement, not just a lint fix).
