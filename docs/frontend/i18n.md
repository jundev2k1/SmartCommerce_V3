# Internationalization Strategy

**Purpose:** How translations are structured so adding a second locale later requires no restructuring, even though only English ships initially.

**Scope:** i18n mechanism and message organization. Not UI component conventions (see [ui-components.md](./ui-components.md)).

**Related documents:** [architecture/folder-structure.md](../architecture/folder-structure.md), [decisions/0008-i18n-strategy.md](../decisions/0008-i18n-strategy.md)

**When to read:** Adding any user-facing text.

**When to ignore:** Non-UI-facing work (services, types, internal tooling).

---

## Library

**next-intl**, chosen over hand-rolled Next.js i18n routing or react-i18next for its native App Router integration (server + client components) and built-in message namespacing. Full comparison in [decisions/0008-i18n-strategy.md](../decisions/0008-i18n-strategy.md).

## Message organization

```
src/i18n/
├── config.ts
└── messages/
    └── en/
        ├── common.json      Shared strings: buttons, generic errors, nav labels
        └── <feature>.json   One file per feature, namespaced to match features/<feature>
```

Every feature that has user-facing text gets its own message namespace (`products.json`, `orders.json`, ...) mirroring `features/<name>` — this keeps translations Feature-First too, so a feature's text lives and moves with its code conceptually, even though physically all locale files sit under `src/i18n/messages/<locale>/` (next-intl expects them there; this is a structural exception to "everything feature-owned lives in `features/`," not a violation of it).

## Rule for all user-facing text

Even though only `en` exists today, **no hardcoded user-facing strings** — always go through `useTranslations('<namespace>')` from day one. This is the entire point of preparing i18n now: retrofitting translation keys into existing components later is far more error-prone than writing them correctly once.

```tsx
const t = useTranslations('products');
<Button>{t('createNew')}</Button>;
```

## Adding a locale later

1. Add `src/i18n/messages/<locale>/*.json` mirroring the `en` structure.
2. Register the locale in `src/i18n/config.ts`.
3. No component code changes — this is the payoff of not hardcoding strings from the start.
