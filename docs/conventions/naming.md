# Naming Conventions

**Purpose:** Eliminate ambiguity about how to name files, folders, components, hooks, services, types, and constants, so every future session produces consistent code without re-deciding these choices.

**Scope:** Naming only. For where a file physically lives, see [architecture/folder-structure.md](../architecture/folder-structure.md). For import rules, see [imports-and-boundaries.md](./imports-and-boundaries.md).

**Related documents:** [architecture/folder-structure.md](../architecture/folder-structure.md), [imports-and-boundaries.md](./imports-and-boundaries.md)

**When to read:** Whenever creating any new file, folder, component, hook, type, or constant.

**When to ignore:** Never fully ignorable, but experienced sessions can skim just the table below instead of the rationale.

---

## Quick reference

| Thing                                      | Convention                                               | Example                                                                    |
| ------------------------------------------ | -------------------------------------------------------- | -------------------------------------------------------------------------- |
| Folders                                    | `kebab-case`                                             | `product-variants/`, `stock-transactions/`                                 |
| Component files                            | `PascalCase.tsx`, matches the component name             | `ProductTable.tsx`, `OrderStatusBadge.tsx`                                 |
| Non-component TS files                     | `kebab-case.ts`                                          | `use-product-filters.ts` is wrong — hooks are the one exception, see below |
| Hooks                                      | `useXxx.ts`, camelCase, always prefixed `use`            | `useProductFilters.ts`, `useAuthSession.ts`                                |
| Service modules (API calls)                | `<feature>.service.ts`                                   | `products.service.ts`                                                      |
| Query hooks / key factories                | `<feature>.queries.ts`                                   | `products.queries.ts`                                                      |
| Types/DTOs                                 | `<feature>.types.ts`                                     | `products.types.ts`                                                        |
| Zod schemas                                | `<feature>.schema.ts`, schema variable suffixed `Schema` | `productSchema`, `createProductSchema`                                     |
| Zustand stores                             | `<name>.store.ts`, hook named `use<Name>Store`           | `theme.store.ts` → `useThemeStore`                                         |
| Constants                                  | `UPPER_SNAKE_CASE`, grouped in `constants.ts`            | `MAX_PAGE_SIZE`, `DEFAULT_LOCALE`                                          |
| Enums / fixed sets                         | `as const` object + derived union type, PascalCase name  | see below — never TS `enum`                                                |
| Feature barrel                             | Always `index.ts` at the feature root                    | `features/products/index.ts`                                               |
| `shared/ui` wrapper components             | `App` prefix + PascalCase                                | `AppButton.tsx`, `AppDialog.tsx`, `AppDataTable.tsx`                       |
| `services/<service>` endpoint files        | `kebab-case`, matches the Swagger `operationId`          | `search-products.ts`, `create-order.ts`                                    |
| `services/<service>` request/response DTOs | PascalCase, matches the Swagger schema name verbatim     | `CreateProductRequest`, `GetOrderResponse`                                 |

## Components

One component per file, file name matches the exported component name exactly (`ProductTable.tsx` exports `ProductTable`). Co-locate a component's own tiny sub-components in the same file only if they're not reused; otherwise give them their own file in `components/`.

## Hooks

Always prefixed `use`, camelCase, one hook per file matching the file name. Business/query hooks live in `features/<feature>/hooks/` or `features/<feature>/api/<feature>.queries.ts`; generic cross-feature hooks live in `shared/hooks/`.

**One documented exception:** `src/shared/hooks/use-mobile.ts` is kebab-case, generated by the shadcn CLI alongside `src/components/ui/sidebar.tsx` (which imports it) — vendored output, not hand-authored, so it wasn't renamed to match this convention. Renaming it risks a future `shadcn add` regeneration silently reintroducing the kebab-case file next to a renamed one. Treat it the same as `src/components/ui/*` — vendored, exempt from this project's own naming rules. Flagged during the Phase 8 consistency review; see [backlog.md](../backlog.md).

## Types and DTOs

Backend-shaped data (once real APIs exist) is suffixed `Dto` (e.g. `ProductDto`) to distinguish it from frontend view-model types (e.g. `ProductListItem`), which carry no suffix. This distinction matters once [api/](../api/README.md) integration begins — until then, mock data types can use the `Dto` suffix directly to keep the eventual swap mechanical.

## `App`-prefixed wrapper components

Every component in `shared/ui` is prefixed `App` (`AppButton`, `AppDialog`, `AppDataTable`, ...). This makes the ADR 0003 wrapper boundary visually unambiguous at every call site — seeing `AppButton` instantly signals "internal wrapper," while a bare `Button` would be easy to confuse with importing shadcn's generated primitive directly. See [frontend/ui-components.md](../frontend/ui-components.md) for the full component list and the button hierarchy built on top of `AppButton`.

## `services/` layer: names mirror the backend, verbatim

Unlike everywhere else in the codebase, `src/services/<service>/` deliberately does **not** rename things to a frontend vocabulary — endpoint file names match the Swagger `operationId`, and DTO type names match the Swagger schema name exactly (`GetProductResponse`, not `ProductDetails`). This keeps the mapping between contract and code mechanical and re-derivable, and avoids drift as the backend contract evolves. Renaming into frontend-friendly terms happens one layer up, in each feature's own query hooks — see [decisions/0012-backend-service-client-layer.md](../decisions/0012-backend-service-client-layer.md).

## Enums — avoid TS `enum`

Prefer a `const` object plus a derived union type over TypeScript's `enum`:

```ts
export const OrderStatus = {
  Pending: 'pending',
  Paid: 'paid',
  Shipped: 'shipped',
  Cancelled: 'cancelled',
} as const;

export type OrderStatus = (typeof OrderStatus)[keyof typeof OrderStatus];
```

Rationale: TS `enum` generates runtime code with non-obvious interop pitfalls (numeric enums, reverse mappings) and doesn't structurally match plain string values coming back from JSON APIs. `as const` unions are erased at compile time, serialize identically to what the backend sends, and work naturally with Zod (`z.enum([...])`).

## Barrel exports

Every feature has exactly one `index.ts` at its root, exporting only the feature's public surface (typically the top-level screen component, and occasionally a hook/type another feature legitimately depends on). Nothing inside `components/`, `hooks/`, or `api/` is imported from outside the feature except through this barrel — see [imports-and-boundaries.md](./imports-and-boundaries.md) for enforcement.

`shared/ui`, `shared/forms`, and other `shared/*` subfolders also expose a single `index.ts` barrel each, so business code imports `@/shared/ui` rather than reaching into individual primitive files.
